Stages of optimization of `LCNF.Code`:
1. `ExplicitRC`: Inserts explicit reference counting increments/decrements into the `Code`.
2. `CSE` (Common Subexpression Elimination): Removes redundant calculations within the `Code`.
3. `CoalesceRC`: Merges multiple RC operations to improve performance.
4. `ElimDead`: Removes unreachable `Code` blocks.

Based on the definition in `src/Lean/Compiler/LCNF/Basic.lean`, here is the mapping of `Code` constructors to JavaScript.

Note that `Code` is designed as a **continuation-passing style** structure: most constructors have a `k : Code pu` (the "next" instruction).

### Mapping: LCNF $\to$ JavaScript

| Constructor | Example in LCNF | Suggested JavaScript Output | Note |
| :--- | :--- | :--- | :--- |
| **`.let`** | `.let (LetDecl.mk x val) k` | `const x = <emit val>;` <br> ` <emit k>` | Create a local variable and continue. |
| **`.fun`** | `.fun (FunDecl.mk f args type val) k` | `function f(<args>) { <emit val> }` <br> `<emit k>` | Define a helper function and continue. |
| **`.jp`** | `.jp (FunDecl.mk j args type val) k` | `function j(<args>) { <emit val> }` <br> `<emit k>` | "Join Point" is just a local function. |
| **`.jmp`** | `.jmp fvarId [arg1, arg2]` | `return fvarId(arg1, arg2);` | Call a function/join-point and return its result. |
| **`.cases`** | `.cases (Cases.mk type res disc alts)` | `switch(disc) { <emit alts> }` | Branch based on the constructor tag. |
| **`.return`** | `.return fvarId` | `return fvarId;` | The final exit point of the function. |
| **`.unreach`** | `.unreach type` | `throw new Error("Unreachable");` | Represents code that can never be hit. |
| **`.inc` / `.dec` / `.del`** | `.inc fvarId 1 true false k` | `/* no-op */` <br> `<emit k>` | **Ignore.** JS Garbage Collector handles this. |
| **`.setTag`** | `.setTag fvarId cidx k` | `fvarId.tag = cidx;` <br> `<emit k>` | Update the constructor tag. |
| **`.oset` / `.uset` / `.sset`**| `.oset fvarId index val k` | `fvarId.args[index] = val;` <br> `<emit k>` | Update a field in the constructor payload. |

### My Opinion on Implementing `ctor` (Constructors)

In Lean, a constructor is not just a class; it's a heap object with a **tag** (the `cidx`) and a **payload** (the arguments). If you implement this as standard JS classes, you will struggle with the `cases` (switch) logic and the `sset/oset` mutations.

**The Wrong Way:** Creating a JS class for every single Lean constructor.
*   *Why:* Too much boilerplate. Lean has thousands of constructors. You can't pre-generate classes for all of them.

**The Right Way: The "Generic Object" Approach**
I recommend implementing a runtime helper function `lean_alloc_ctor` and treating constructors as plain JS objects.

#### Suggested Implementation:
```javascript
// Runtime Helper
function lean_alloc_ctor(tag, args) {
    return {
        tag: tag,
        args: args // Array of values
    };
}

// Example of a Lean Constructor: Option.some (x)
// LCNF: .let (x_val) ... -> .let (res) (ctor {cidx: 1, size: 1} [x_val])
const x_val = 42;
const res = lean_alloc_ctor(1, [x_val]);

// Example of a Lean Case match:
// LCNF: .cases (disc: res) [ alt(cidx: 1, code: ...), default(...) ]
switch(res.tag) {
    case 1:
        // Handle Option.some: the value is in res.args[0]
        console.log(res.args[0]);
        break;
    default:
        // Handle Option.none
        break;
}
```

#### Why this is the best approach for JS:
1.  **Dynamic:** It handles any constructor (even from libraries you haven't seen yet) because it only cares about the `tag` and the `args` array.
2.  **Mutation Friendly:** The `oset` / `uset` / `sset` instructions in LCNF simply become `obj.args[i] = val`, which is extremely fast in JS.
3.  **Memory Efficient:** JS engines optimize "shapes" (hidden classes). Since most constructors will have the same shape `{ tag: number, args: array }`, the JS engine will optimize this heavily.
4.  **Direct Mapping:** It maps 1:1 to how `EmitC` works, but replaces C++ pointer arithmetic with JS array indexing.

**Final Recommendation:**
When you build `EmitEs6`, don't try to be "too JavaScripty" by creating classes. Stay close to the Lean runtime model (Tag + Payload), and let the JS Garbage Collector handle the memory.

> and if we go with Decl? how then?

If you decide to bypass LCNF and go directly from **`Decl` (and its underlying `Expr` trees)** to JavaScript, you are essentially building a "Source-to-Source" compiler rather than a "Backend Emitter."

Here is how that would work, and the price you would pay in terms of implementation effort.

### 1. The Mechanism: Recursive Traversal
Since `Expr` is a recursive tree, your generator must be a recursive function. You would walk the tree from the root down to the leaves.

**Conceptual Mapping:**

| Lean `Expr` | JavaScript Output |
| :--- | :--- |
| `Expr.app(fn, args)` | `fn(...args)` |
| `Expr.lam(binder, body)` | `(binder) => { return <emit body>; }` |
| `Expr.let(name, val, body)` | `const name = <emit val>; <emit body>` |
| `Expr.case(disc, alts)` | `switch(<emit disc>) { <emit alts> }` |
| `Expr.ctor(tag, args)` | `lean_alloc_ctor(tag, <emit args>)` |
| `Expr.const(name)` | `lean_runtime_get_const(name)` |

---

### 2. The "Hidden" Work (What you must implement)

If you use `Code`, the Lean compiler has already solved these problems. If you use `Decl`, **you must write the code for these yourself**:

#### A. De Bruijn Index Resolution (The hardest part)
Lean `Expr` does not use names like `x` or `y` internally; it uses **De Bruijn indices** (e.g., "the variable 2 levels up").
*   **In `Code`**: Variables are already renamed to unique names (e.g., `v_1`, `v_2`).
*   **In `Decl`**: You must maintain a `LocalContext` stack while recursing. When you see "variable 2", you have to look up in your stack what the name of that variable was and print that name in JS.

#### B. Lambda Lifting & Closures
In Lean, functions can be nested.
`def outer x := let inner y := x + y in inner 10`
If you just recurse, you might get:
```javascript
function outer(x) {
  const inner = (y) => x + y;
  return inner(10);
}
```
While this works in JS, it doesn't match how Lean's runtime expects functions to be structured (Lean expects functions to be "lifted" to the top level and passed their environment as an explicit object). If you want your JS to be compatible with other Lean runtime helpers, you'd have to implement **Lambda Lifting** yourself.

#### C. Expression Flattening
Since you are recursing, a deeply nested Lean expression:
`f(g(h(i(j(k(x))))))`
will produce a deeply nested JS call. For very large expressions, this can lead to stack overflows during the *compilation* phase (the JS generator itself crashing) or the *execution* phase.

---

### 3. Comparison: `Decl` vs `Code`

| Feature | `Decl` $\to$ JS (Recursive) | `Code` $\to$ JS (Linear) |
| :--- | :--- | :--- |
| **Logic** | Recursive Tree Walk | Linear Loop / Sequence |
| **Variable Names**| You must resolve indices $\to$ names | Names are already provided |
| **Nesting** | Deeply nested JS code | Flat, `const`-heavy JS code |
| **Optimizations** | None (unless you write them) | Gets RC-cleanup, CSE, and Dead-code removal |
| **Implementation** | Complex (requires `LocalContext`) | Simple (mirrors `EmitC.lean`) |
| **Control** | High (you control the structure) | Low (you follow Lean's plan) |

### Final Verdict

**Go with `Decl` if:** You want to create a "Lean-to-JS" transpiler that looks like high-level JavaScript and you don't care about matching the Lean runtime's exact execution model.

**Go with `Code` if:** You want a professional, optimized compiler that is guaranteed to behave exactly like the C++ version and takes advantage of the work the Lean team has already put into the LCNF pipeline.

**My professional advice:** Unless you have a very specific reason to avoid LCNF, **do not use `Decl`**. The "price" of resolving De Bruijn indices and handling lambda lifting is very high compared to the simplicity of printing a flat list of `Code` instructions.

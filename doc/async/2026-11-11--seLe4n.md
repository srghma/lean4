# kernel for QEMU’s ARM64  is built from what? where is the entry point? in rust code or in lean code?


1. **Hardware entry:** `_start` in [`boot.S`](https://github.com/hatter6822/seLe4n/blob/5d1bcfe6fae0833bbcde3d55d90f5d24070a5a97/rust/sele4n-hal/src/boot.S#L21-L25). QEMU loads the image and begins executing here.
2. **Rust boot entry:** `_start` sets up the boot environment, then calls `rust_boot_main` in [`boot.rs`](https://github.com/hatter6822/seLe4n/blob/5d1bcfe6fae0833bbcde3d55d90f5d24070a5a97/rust/sele4n-hal/src/boot.rs#L74-L91). Rust initializes the hardware and Lean runtime.
3. **Lean kernel entry:** after runtime initialization, Rust calls the exported `lean_kernel_main_qemu_virt`, defined by [`QemuVirt/KernelMain.lean`](https://github.com/hatter6822/seLe4n/blob/5d1bcfe6fae0833bbcde3d55d90f5d24070a5a97/SeLe4n/Platform/QemuVirt/KernelMain.lean#L28-L34). That Lean function handles the `virt` device tree and installs the kernel state.

For the **Lean-linked** QEMU image, the build first produces the AArch64 Lean archive, then Cargo builds the `sele4n-kernel` binary with `hw_target`, `kernel_image`, and `board_qemu_virt` enabled. The HAL’s build script links the Lean archive into that Rust binary. The repo’s supported build-and-boot route is:

```bash
./scripts/test_lean_aarch64_archive.sh
./scripts/test_qemu.sh --lean-kernel
```

Without `hw_target` (as in the HAL-only image), it’s still the Rust/assembly image, but it does **not** contain the Lean kernel.


# explain sys_read from linux

<details>
  Here is the line-by-line explanation of both functions.

---

### Part 1: `ksys_read`

```c
ssize_t ksys_read(unsigned int fd, char __user *buf, size_t count)
```
* **`ssize_t`**: Returns a signed size — positive value indicates the number of bytes successfully read; a negative value indicates an error (e.g., `-EBADF`).
* **`unsigned int fd`**: The integer file descriptor passed by the userspace program.
* **`char __user *buf`**: Pointer to the destination buffer in userspace. The `__user` attribute is a static analysis marker telling the compiler/Sparse: *"This pointer comes from untrusted userspace; do not dereference it directly."*
* **`size_t count`**: The maximum number of bytes requested to read.

---

```c
CLASS(fd_pos, f)(fd);
```
* Uses modern Linux kernel **RAII** (cleanup attribute macros).
* Looks up the integer `fd` in the process's descriptor table and wraps the resulting `struct file *` into variable `f`.
* Crucially, the `fd_pos` variant also **acquires the file position lock (`f_pos_lock`)** to prevent concurrent threads from racing on the file offset (`f_pos`).
* When `f` leaves scope (when `ksys_read` returns), its destructor automatically runs: releasing the lock and dropping file reference counts without needing manual cleanup on every error exit.

---

```c
ssize_t ret = -EBADF;
```
* Sets the default return value to `-EBADF` (*"Bad file descriptor"*). If the `fd` is invalid or not open, the function skips the `if` block and returns this error directly.

---

```c
if (!fd_empty(f)) {
```
* Checks if the descriptor lookup was successful (i.e., `f` actually holds a valid `struct file *`).

---

```c
loff_t pos, *ppos = file_ppos(fd_file(f));
```
* `fd_file(f)` extracts the underlying `struct file *` from the RAII wrapper `f`.
* `file_ppos(...)` checks if this file has a seekable position:
  * For **streams** (pipes, sockets, terminals), it returns `NULL` (they have no seekable position).
  * For **regular files**, it returns the address `&file->f_pos`.
* `pos` is an uninitialized local stack variable representing a 64-bit file offset (`loff_t`).

---

```c
if (ppos) {
    pos = *ppos;
    ppos = &pos;
}
```
* **Why this copy happens:**
  Instead of letting lower layers modify `file->f_pos` directly, it copies the current offset into the local stack variable `pos` and points `ppos` to `&pos`.
  If the read operation fails halfway through with an error, the real `file->f_pos` remains untouched and uncorrupted.

---

```c
ret = vfs_read(fd_file(f), buf, count, ppos);
```
* Calls into the Virtual Filesystem layer (`vfs_read`) to perform the actual read operation.
* Passes the file object, the userspace buffer, byte count, and pointer to the temporary offset `ppos`.

---

```c
if (ret >= 0 && ppos)
    fd_file(f)->f_pos = pos;
```
* If the read was successful (`ret >= 0`) and the file has a position (`ppos != NULL`), it permanently commits the updated offset `pos` back to `file->f_pos`.

---

```c
}
return ret;
```
* Returns the number of bytes read (or negative error code) to userspace.
* Right here at the closing brace `}`, the `CLASS(fd_pos, f)` destructor fires, unlocking the file.

---

### Part 2: `vfs_read`

```c
ssize_t vfs_read(struct file *file, char __user *buf, size_t count, loff_t *pos)
```
* The core entry point for reading in the Virtual Filesystem. Operates on an already-resolved `struct file *` rather than an integer `fd`.

---

```c
if (!(file->f_mode & FMODE_READ))
    return -EBADF;
```
* Verifies file permissions. Checks if the file was opened with read capabilities (e.g., `O_RDONLY` or `O_RDWR`).
* If someone opened a file with `O_WRONLY` and calls `read()`, it rejects the call with `-EBADF`.

---

```c
if (unlikely(!access_ok(buf, count)))
    return -EFAULT;
```
* **`unlikely(...)`**: A compiler optimization hint indicating that valid programs almost never hit this branch (branch predictor optimization).
* **`access_ok(buf, count)`**: Essential **security check**. It verifies that the entire address range `[buf, buf + count)` belongs strictly to **userspace** memory.
* If a malicious user program passes a kernel memory address in `buf` to trick the kernel into overwriting kernel memory, `access_ok()` catches it and returns `-EFAULT` (*"Bad address"*).

---

```c
ret = rw_verify_area(READ, file, pos, count);
if (ret)
    return ret;
```
* Performs higher-level policy and sanity checks:
  1. Checks for arithmetic overflow (e.g., `pos + count` wrapping around 64-bit integer limits).
  2. Calls Linux Security Modules (LSM) hooks like **SELinux**, **AppArmor**, or POSIX mandatory file locks to check if this read is permitted.
  3. Triggers filesystem event monitoring notifications (`fsnotify`).
* If any security check fails, it immediately aborts and returns the error code (e.g., `-EACCES`, `-EOVERFLOW`, `-EINVAL`).

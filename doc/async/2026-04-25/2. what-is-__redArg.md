Sure. The key point is:

* `List.isEmpty` in Lean is **polymorphic**: `List α → Bool`
* but the generated code wants a **monomorphic / optimized** worker that doesn’t even receive the unused `α`.

So Lean generates **two layers**: a real implementation (`___redArg`) and a wrapper (`isEmpty`) that matches the original Lean signature.

### What’s the *difference* between these 4 functions?

* `l_List_isEmpty___redArg`
  **real implementation**, takes only the list, returns unboxed `uint8_t`.

* `l_List_isEmpty___redArg___boxed`
  same as above, but returns a boxed Lean Bool (`lean_object*`).

* `l_List_isEmpty`
  **API wrapper** that matches Lean signature (`α` + list), but ignores `α`.

* `l_List_isEmpty___boxed`
  boxed version of the API wrapper.

### Why does Lean do this?

Because:

* Lean source code has extra parameters (like `α`) that vanish logically,
* but compiled calling conventions still need to support polymorphic calls,
* and runtime wants fast specialized workers without unused arguments.

So `___redArg` is the optimized worker, and `isEmpty` is the compatibility wrapper.

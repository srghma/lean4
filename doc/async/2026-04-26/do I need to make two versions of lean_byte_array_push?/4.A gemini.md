### 1. Rust vs Lean

You are exactly right that Rust uses affine/linear types (Ownership).
Because Rust exposes this in the type system, there is no runtime reference counter (unless you specifically opt-in with `Rc<T>`). In Rust, the **programmer** chooses the variant by the function signature:

```rust
// Variant 1: Consumes the array (mutates and returns it)
fn push_reusing(mut arr: Vec<i32>, v: i32) -> Vec<i32> {
    arr.push(v);
    arr
}

// Variant 2: Borrows the array (immutably), forces a copy
fn push_immutable(arr: &Vec<i32>, v: i32) -> Vec<i32> {
    let mut new_arr = arr.clone();
    new_arr.push(v);
    new_arr
}
```

If a Rust programmer tries to use `push_reusing` on `init` twice, the Rust compiler throws an error (`use of moved value`).

In Lean, the programmer writes pure functional code and never thinks about memory. The Lean compiler automatically inserts `lean_inc` / `lean_dec`. Because the choice happens at **runtime**, you only need **one** C++ function that handles both paths depending on the RC.

If you are writing a JavaScript backend without RC, and you want to do what Rust does automatically, yes: your JS backend would need to perform static analysis on the Lean IR, determine which arrays are used linearly, and explicitly emit `lean_array_push__reusing(arr, v)` instead of `lean_array_push(arr, v)`.

### 2. `append(a, b)` variants

You noticed a brilliant theoretical optimization! If `a` is shared (RC > 1) but `b` is exclusive (RC == 1), could we mutate `b` to prepend `a`?

In theory, yes! But prepending to an array requires shifting every element in `b` to the right to make room for `a`. That is an `O(b.length)` operation. Allocating a brand new array `c` and copying `a` and `b` is _also_ `O(a.length + b.length)`. Because the performance difference between prepending and allocating is very small, Lean's C++ implementation does **not** actually do this. `lean_array_append` only checks if `a` is exclusive.

If you were writing this for JS using static analysis, you _could_ theoretically implement 3 variants:

```js
function lean_array_append__reuse_a(a, b) { a.push(...b); return a; }
function lean_array_append__reuse_b(a, b) { b.unshift(...a); return b; }
function lean_array_append__copy(a, b)    { return a.concat(b); }
```

But honestly, because `unshift` is so slow in JS engines!!!!, `a.concat(b)` is usually much faster than `reuse_b` anyway!

### 3. Does the C++ compiler optimize the RC checks at compile time?

Let's look at `x := ([].push 1).push 2` again.

Lean's internal compiler _does_ perform static analysis to eliminate unnecessary `inc` and `dec` calls. Notice in the C++ code I showed earlier for Test 1, Lean **did not** emit any `lean_inc` calls! It statically knew the array was used linearly.

However, does the C++ compiler (Clang/GCC) optimize away the `if (lean_is_exclusive(a))` check inside `lean_array_push`?
**No, it usually doesn't.**
`lean_array_push` is an opaque C function compiled in the Lean runtime library. When it is called, the CPU actually executes the `if (RC == 1)` check at runtime.
Why is this okay? Because reading an integer (`RC`) and comparing it to `1` takes less than a nanosecond, and CPU branch predictors will predict the outcome with 100% accuracy in straight-line code. The cost of the check is completely negligible compared to the cost of allocating an array.

If you are generating JavaScript, the exact same principle applies. If you don't want to build a complex static analyzer, you can just emulate Lean's RC in JS. It is much easier to just add an `rc` field to your arrays, emit `inc`/`dec` exactly where Lean tells you to, and do the check at runtime!

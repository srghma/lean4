### 1) Rust vs Lean: who writes the “reusing” variant?

In **Rust**, the *type system* forces the distinction.

* If a function takes `Vec<T>` **by value**, Rust knows the caller gives up ownership, so the function can mutate it in-place.
* If a function takes `&Vec<T>` (shared borrow), it must not mutate it.
* If it takes `&mut Vec<T>` (exclusive borrow), it may mutate it.

So in Rust, you typically **don’t need runtime `is_exclusive` checks** like Lean does. The compiler knows statically.

Example:

```rust
fn push_reuse(mut v: Vec<i32>, x: i32) -> Vec<i32> { // Owned input (this is not useless function, bc returns, but better use &mut Vec<i32>)
    v.push(x);      // in-place
    v
}

fn push_reuse2(v: &mut Vec<i32>, x: i32) { // Exclusive borrow
    v.push(x);   // in-place
}

fn push_copy(v: &Vec<i32>, x: i32) -> Vec<i32> { // Shared borrow
    let mut out = v.clone(); // copies
    out.push(x);
    out
}

fn push_owned2(mut v: Vec<i32>, x: i32) { // useless function. Doesnt return anything. v is lost.
    v.push(x);
    drop(v); // memory freed here
    // heavy work after
}
```

So yes: **in Rust, the “two variants” are explicit in the signature**.

Rust is *affine* (values can be dropped implicitly), but ownership gives you the same “exclusive vs shared” info **statically**, not via runtime refcount checks like Lean.

### 2) About `append(a, b)` and reusing `b`

```js
function append(a, b) {
  if (a._rc === 1) {
    // reuse a
    a.data.push(...b.data);
    return a;
  } else if (b._rc === 1) {
    // reuse b, but need to prepend a
    b.data = a.data.concat(b.data);
    return b;
  } else {
    // allocate new
    return { _rc: 1, data: a.data.concat(b.data) };
  }
}
```

BUT BETTER

```js
// zip : Array α -> Array β -> Array (α×β)
function zip(a, b) {
  const n = Math.min(a.data.length, b.data.length);

  if (a._rc === 1) {
    // reuse a
    for (let i = 0; i < n; i++) {
      a.data[i] = [a.data[i], b.data[i]];
    }
    a.data.length = n;
    return a;
  } else if (b._rc === 1) {
    // reuse b
    for (let i = 0; i < n; i++) {
      b.data[i] = [a.data[i], b.data[i]];
    }
    b.data.length = n;
    return b;
  } else {
    // allocate new
    const out = new Array(n);
    for (let i = 0; i < n; i++) {
      out[i] = [a.data[i], b.data[i]];
    }
    return { _rc: 1, data: out };
  }
}
```


#### Can it improve even more?

Yes: you can optimize by checking capacity / reserved space, like C++ `std::vector` does. Lean’s runtime arrays *do* have a capacity field.

So a more realistic optimized append is:

* if exclusive and capacity sufficient: mutate
* if exclusive but capacity insufficient: reallocate (still “reuse” header but allocate new data)
* otherwise allocate fresh

That’s basically what a good `push`/`append` does.

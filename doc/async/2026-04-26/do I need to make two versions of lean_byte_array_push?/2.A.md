Lean's approach to in-place mutation, "Counting Immutable Beans", is incredibly elegant precisely because it avoids the need for compile-time linear type checking.

Here is the breakdown of what actually happens, and how you can apply this to your JS generator.

### What is actually happening in Lean?
Lean does **not** generate two versions of `lean_array_push`. Instead, the decision to mutate or copy is made **at runtime**.

When Lean generates C++ code, it relies on a hidden reference counter (RC) attached to every object. At runtime, the single C++ `lean_array_push` function looks like this:
```cpp
lean_obj_res lean_array_push(lean_obj_arg a, lean_obj_arg v) {
    if (lean_is_exclusive(a)) { // Checks if RC == 1
        // ... mutate in place ...
        return a;
    } else {
        // ... allocate new array, copy elements, add v ...
        lean_dec_ref(a); // Consumes the reference
        return new_a;
    }
}
```

### Checking your tests
I just compiled your two tests into C++ to see exactly what Lean emits. Here is the answer to your question:

**Possibility 3 happens**: `init` is copied for `x`, and then mutated in-place for `y`.

Here is the generated C++ for **Test 2**:
```c
v_init_11_ = lean_array_push(v_empty, v_x); // create init
lean_inc_ref(v_init_11_); // RC becomes 2 because `init` is used for both `a` and `b`

v_a_12_ = lean_array_push(v_init_11_, v_y);
// ^ Inside lean_array_push, RC is 2. So it allocates a COPY, pushes y, and then calls lean_dec_ref(init), reducing RC back to 1.

v_b_15_ = lean_array_push(v_init_11_, v___x_14_);
// ^ Inside lean_array_push, RC is now 1! So it mutates the array IN-PLACE and returns it!
```
Notice how Lean emitted `lean_inc_ref` to track that `init` is used twice. The C++ function then dynamically checked the RC to figure out whether it could optimize.

### Why this is brilliant
Because the optimization happens at runtime via RC, it automatically works for arrays passed through complex control flows, loops, and external functions where static analysis would fail. If you pass an array into a function, and the caller drops their reference (RC=1), the function will mutate it. If the caller keeps a reference (RC=2), the function copies it.

### How to apply this to JavaScript?
In JavaScript, we **cannot read the garbage collector's reference count** (engines like V8 completely hide it). Because we don't have a `lean_is_exclusive` equivalent in JS, a naive JS port must always assume the array is shared and copy it using `.slice()`.

If you want to implement the optimization in your JS generator, you have a few choices:
1. **Manual Reference Counting in JS**: You can make Lean's compiler emit explicit `inc` and `dec` calls into JavaScript, and wrap your JS arrays in a custom object: `{ rc: 1, data: [] }`. Then you can implement `lean_array_push` exactly like C++ does. (This adds runtime overhead but unlocks the exact Lean optimization).
2. **Static Analysis Pass (Your idea)**: If you can write a static analysis pass over Lean's LCNF (the intermediate representation) that detects when a variable is strictly used linearly (never `inc`'d), you could emit a call to `lean_array_push__reusing`. However, because Lean 4 relies on runtime RC, it doesn't currently do this static analysis for arrays for you.
3. **Always copy**: This is what the current Lean JS emitter does. If you look inside `EmitEs6.lean`, any `isShared` LCNF instruction is currently hardcoded to compile to `true`, forcing the safe, copying path.

### What about 4 variants if there are 2 arguments?
If you have a function with two arrays (like `Array.append(a, b)`), the C++ implementation just does:
```cpp
if (lean_is_exclusive(a)) {
    // mutate a to include b
} else {
    // allocate new array c, copy a into c, copy b into c
}
```
It usually only checks exclusivity on the "destination" parameter! There's no need for 4 variants.

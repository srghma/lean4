Based on the 2026 paper (*"Same Coeffect, Different Base: Connecting Two Dominant Approaches to Graded Types"*) and the Granule codebase, here is a detailed breakdown answering your questions:

---

### 1. Is the idea to show that Linear Push Core is isomorphic to Graded Modal Core?

**Partially, but with an important distinction:**

* **The broader goal of the paper**: To establish a comprehensive bridge between the **two dominant lineages of graded type systems**:
  1. **Linear-base lineage** ($\text{LB} \subseteq \text{LC} \subseteq \text{LPC}$): Functions are linear by default ($A \multimap B$), and coeffects/grades are packaged into a modality ($\Box_r A$).
  2. **Graded-base lineage** ($\text{GB} \subseteq \text{GMB} \subseteq \text{GMC}$, and $\text{GPB}$): Arrows are pervasively graded ($A \xrightarrow{r} B$).

* **Why Linear *Push* Core (LPC)?**
  * At the base level, **Linear Base ($\text{LB}$)** and **Graded Modal Base ($\text{GMB}$)** enjoy an **observational isomorphism** ($\text{LB} \cong \text{GMB}$, [ObservationalIso.lean](file:///home/srghma/projects/lean-melearning-Same%20Coeffect,%20Different%20Base-Connecting%20Two%20Dominant%20Approaches%20to%20Graded%20Types-2026/RequestProject/Sec3/Translations/ObservationalIso.lean#L7-L52)).
  * However, when moving to core calculi with products ($\otimes, \times$) and sums ($\oplus, +$), the naive translation $\text{GMC} \to \text{LC}$ is **unsound** (the $\times$ arrow in [diagram.mermaid](file:///home/srghma/projects/lean-melearning-Same%20Coeffect,%20Different%20Base-Connecting%20Two%20Dominant%20Approaches%20to%20Graded%20Types-2026/diagram.mermaid#L47) and [arrow_GMC_LC_unsound](file:///home/srghma/projects/lean-melearning-Same%20Coeffect,%20Different%20Base-Connecting%20Two%20Dominant%20Approaches%20to%20Graded%20Types-2026/RequestProject/Diagram.lean#L137-L144)). This is because pattern matching in $\text{GMC}$ automatically distributes modalities over pairs, which Linear Logic/$\text{LC}$ forbids.
  * Adding explicit distributivity constructs ($\text{push}_\otimes, \text{push}_\oplus, \text{push}_{\mathrm{unit}}$) yields **Linear Push Core ($\text{LPC}$)** ([products-sums-ottput.tex](file:///home/srghma/projects/lean-melearning-Same%20Coeffect,%20Different%20Base-Connecting%20Two%20Dominant%20Approaches%20to%20Graded%20Types-2026/products-sums-ottput.tex#L345-L365)).
  * $\text{LPC}$ and $\text{GMC}$ have **mutual sound embeddings/translations** ($\text{LPC} \leftrightarrow \text{GMC}$) that preserve typing and simulate reduction steps ([arrow_GMC_LPC](file:///home/srghma/projects/lean-melearning-Same%20Coeffect,%20Different%20Base-Connecting%20Two%20Dominant%20Approaches%20to%20Graded%20Types-2026/RequestProject/Diagram.lean#L145-L151)).

### 2. Does Granule use Linear Push Core by default, and switch to Graded Modal Core via `language GradedBase`?

* **By default: YES, Granule is Linear Push Core ($\text{LPC}$)**.
  * In default Granule, unadorned arrows `a -> b` are linear, and coeffects live in the modality `a [r]`.
  * Moreover, Granule's pattern matching implicitly distributes box modalities over constructors and tuples (e.g. `let [(x, y)] = p in ...`). As noted in §5.4 and §6.1 of the paper ([discussion-ottput.tex:L72-L78](file:///home/srghma/projects/lean-melearning-Same%20Coeffect,%20Different%20Base-Connecting%20Two%20Dominant%20Approaches%20to%20Graded%20Types-2026/discussion-ottput.tex#L72-L78) and [products-sums-ottput.tex:L360-L362](file:///home/srghma/projects/lean-melearning-Same%20Coeffect,%20Different%20Base-Connecting%20Two%20Dominant%20Approaches%20to%20Graded%20Types-2026/products-sums-ottput.tex#L360-L362)):
    > *"Granule is a linear-base system by default... Granule achieves the same expressivity [as push] implicitly via pattern matching."*

* **With `language GradedBase`: It switches to Graded Base / Graded Poly Base, NOT Graded Modal Core**.
  * When you enable `language GradedBase` in Granule ([examples/graded-base.gr](file:///home/srghma/projects/granule/examples/graded-base.gr#L1-L10)), the arrow itself becomes graded (`a % r -> b`), matching the syntax and semantics of **Graded Base ($\text{GB}$)** ([discussion-ottput.tex:L86-L95](file:///home/srghma/projects/lean-melearning-Same%20Coeffect,%20Different%20Base-Connecting%20Two%20Dominant%20Approaches%20to%20Graded%20Types-2026/discussion-ottput.tex#L86-L95)).
  * In the formal calculi, **Graded Modal Core ($\text{GMC}$)** has an explicit primitive box modality ($\Box_r A$) alongside graded arrows. But in Granule with `GradedBase`, coeffects are placed directly on function arrows or encoded into data types, rather than using primitive modal boxes.
  * Because Granule supports polymorphism (`forall {a : Type}`), Granule under `language GradedBase` corresponds formally to **Graded Poly Base ($\text{GPB}$)** combined with data types ([introduction-ottput.tex:L130-L135](file:///home/srghma/projects/lean-melearning-Same%20Coeffect,%20Different%20Base-Connecting%20Two%20Dominant%20Approaches%20to%20Graded%20Types-2026/introduction-ottput.tex#L130-L135)).

### 3. Did only Graded Poly Base (GPB) have type polymorphism / System F / term-on-type dependence?

**YES, exactly correct within the formal calculi of the paper.**

* Among the **7 formal calculi** studied in the paper:
  * **Linear lineage**: Linear Base ($\text{LB}$), Linear Core ($\text{LC}$), Linear Push Core ($\text{LPC}$) — *all simply-typed / monomorphic*.
  * **Graded lineage**: Graded Base ($\text{GB}$), Graded Modal Base ($\text{GMB}$), Graded Modal Core ($\text{GMC}$) — *all simply-typed / monomorphic*.
  * **Graded Poly Base ($\text{GPB}$)**: The **only calculus** in the paper with System F type polymorphism ([Syntax.lean](file:///home/srghma/projects/lean-melearning-Same%20Coeffect,%20Different%20Base-Connecting%20Two%20Dominant%20Approaches%20to%20Graded%20Types-2026/RequestProject/Sec4/Poly/Syntax.lean#L8-L20)):
    $$\text{Terms: } t ::= \dots \mid \Lambda \alpha.\, t \mid t\ @\ A \qquad \text{Types: } A ::= \dots \mid \alpha \mid \forall \alpha.\, B$$

* **Why GPB was introduced**:
  Translating $\text{LB} \to \text{GB}$ in direct style (without a global CPS transformation) requires Church-encoding the graded modality $\Box_r A$:
  $$\Box_r A \triangleq \forall \beta.\ (A \xrightarrow{r} \beta) \xrightarrow{1} \beta$$
  which requires System F type abstraction ($\forall \beta$).

* **Consequence in the diagram**:
  In `linear-calculi-diagram.pdf` (and [diagram.mermaid:L48-L49](file:///home/srghma/projects/lean-melearning-Same%20Coeffect,%20Different%20Base-Connecting%20Two%20Dominant%20Approaches%20to%20Graded%20Types-2026/diagram.mermaid#L48-L49)), translations from $\text{GPB}$ back to $\text{LC}$ or $\text{LPC}$ are marked:
  $$\text{GPB} \dashrightarrow \text{LC / LPC} \quad \text{\textbf{❌ Impossible: Target lacks }} \forall$$
  precisely because none of the other formal core or base calculi support type quantification.

### Short Answer

* **When Linear Push Core is used (default Granule):** **No.** 
  In default Granule, function arrows are strictly linear (`->`). The graded arrow syntax `% r ->` is rejected by the typechecker in linear-base mode.
* **When `language GradedBase` is used:** **Yes (syntactically and semantically).** 
  Granule allows `% 1 ->`, and also allows the box modality `a [...]`. However, in Graded Base it is redundant: you would normally just write `a % ω -> b`.

---

### Detailed Breakdown

#### 1. Under Linear Push Core (Default Granule)

In the linear-base lineage ($\text{LB} \subseteq \text{LC} \subseteq \text{LPC}$):
* **Function arrows are strictly linear ($A \multimap B$):** In Granule, this is written simply with the unadorned arrow `->`.
* **Grades belong exclusively to the modality ($\Box_r A$):** In Granule, this is written `a [r]`.
* If you write `a [ω] % 1 -> b`:
  * Although the parser accepts the token sequence in [Parser.y:L400](file:///home/srghma/projects/granule/frontend/src/Language/Granule/Syntax/Parser.y#L400) (`Type '%' Coeffect '->' Type`), the typechecker's lambda rule in default mode ([Checker.hs:L569](file:///home/srghma/projects/granule/frontend/src/Language/Granule/Checker/Checker.hs#L569)) explicitly requires `FunTy _ Nothing sig tau` (meaning **no grade annotation on the arrow**).
  * A function checked against an arrow with an explicit grade (`FunTy _ (Just 1) ...`) is rejected because graded arrows are not part of the linear-base typing judgment ($\vdash_l$).

**How to write it in default Granule:**
```granule
f : forall {a : Type, b : Type} . a [Inf] -> b
f [x] = ...  -- x is used with coeffect Inf (ω)
```
*(The `->` arrow is implicitly linear, i.e. consumed with usage $1$.)*

---

#### 2. Under `language GradedBase`

When `language GradedBase` is enabled:
* The core typing judgment switches to the graded-base lineage ($\vdash_g$).
* The arrow itself carries the grade: `A % r -> B` corresponds to $A \xrightarrow{r} B$.
* In Granule's implementation, the box modality `a [r]` is **not disabled** when `language GradedBase` is turned on (see [negative/simple/set.gr](file:///home/srghma/projects/granule/frontend/tests/cases/negative/simple/set.gr#L7-L17)).

If you write:
```granule
language GradedBase

f : forall {a : Type, b : Type} . a [Inf] % 1 -> b
f [x] = ...
```

* **What happens during typechecking:**
  When pattern-matching on `[x]`, Granule calls `flattenCoeffects` ([Patterns.hs:L175, L387](file:///home/srghma/projects/granule/frontend/src/Language/Granule/Checker/Patterns.hs#L175)):
  $$\text{grade}(x) = \text{outer grade} \cdot \text{inner grade} = 1 \cdot \omega = \omega$$
  Variable `x` is bound in the environment at grade $\omega$, exactly as expected.

* **Why this is redundant in Graded Base:**
  The whole point of the Graded Base approach is to **eliminate the modal box syntactic overhead**. Instead of wrapping the type in a modality `[ω]` and passing it with a linear arrow `% 1 ->`, you directly grade the function arrow:
  ```granule
  language GradedBase

  f : forall {a : Type, b : Type} . a % Inf -> b
  f x = ...    -- x is directly available at grade Inf (no unboxing pattern [x] needed)
  ```

### Summary in Terms of the Paper's 7 Calculi

| Calculus / Mode in Granule | Arrow Syntax | Modality Syntax | Can you write `a [ω] % 1 -> b`? |
| :--- | :--- | :--- | :--- |
| **Linear Push Core** (default) | `a -> b` ($\multimap$) | `a [r]` ($\Box_r a$) | **No** (graded arrows `% r ->` are not in $\text{LPC}$) |
| **Graded Base / GPB** (`language GradedBase`) | `a % r -> b` ($\xrightarrow{r}$) | Redundant (use `% r ->`) | **Yes**, but idiomatically written `a % Inf -> b` |
| **Graded Modal Core ($\text{GMC}$)** | `a % r -> b` ($\xrightarrow{r}$) | `a [r]` ($\Box_r a$) | **Yes** (this is precisely having both $\Box_r$ and $\xrightarrow{s}$) |

### 3. Linearity vs Uniqueness: "Future" vs "Past" ($R \le 1$)

Your intuition is **spot on**, and Granule’s typechecker is designed explicitly around this distinction:

#### The Duality: Future vs Past
* **Linearity / Coeffects ($R \le 1$ or $R = 1$) are about the FUTURE:**
  A linear type judgment $\Gamma \vdash e : A$ is a contract on the **continuation** (how $e$ will be consumed downstream).
  It says: *"I promise that whoever holds this reference will evaluate/consume it at most once."*
* **Uniqueness ($*A$) is about the PAST / Topology:**
  A uniqueness guarantee is a statement about **heap aliasing and sharing history**.
  It says: *"At this moment, this pointer is the sole incoming reference to this object in the entire heap."*

#### Why $R \le 1$ does NOT equal Uniqueness
Suppose object $O$ in memory has two pointers, $x$ and $y$:
* You can give $x$ the type $A [0..1]$ (or $R \le 1$). $x$ guarantees that *it* will only be read once.
* But $O$ is **not unique**, because pointer $y$ also exists!
* If you perform an in-place mutation on $x$ under the mistaken belief that $R \le 1 \implies \text{Unique}$, you will destroy the value under pointer $y$, violating referential transparency.

#### How Granule Formalizes This
Granule does **not** model uniqueness as a coeffect semiring ($R \le 1$). Instead:
1. Coeffects are comonadic modalities ($\Box_r A$ / `a [r]`) tracking **future usage**.
2. Uniqueness is a guarantee modality (`*A` / `a *{Unique}`) tracking **reference isolation**.

Granule's typechecker explicitly enforces this separation. In [`Language/Granule/Checker/Monad.hs:L867`](file:///home/srghma/projects/granule/frontend/src/Language/Granule/Checker/Monad.hs#L867), if you attempt to treat uniqueness as a coeffect, the compiler throws:
> *"Cannot promote non-unique value of type `t` to unique, **since uniqueness is not a coeffect**."*

You can safely convert a unique reference into a linear/graded reference because absence of aliases implies $\le 1$ future use ([`uniqueReturn : *a -> a [r]`](file:///home/srghma/projects/granule/frontend/src/Language/Granule/Checker/Primitives.hs#L662)), but the reverse is strictly prohibited.

### Part 1: Deep Dive into `Star`, `Borrow`, `Guarantee`, and `Permission`

In Granule, **Uniqueness** and **Borrowing** form an ownership-and-permission subsystem alongside coeffects.

#### `Star` vs `Borrow`
* **`Star :: Guarantee -> Type -> Type`**:
  * **What it is:** The **uniqueness / ownership guarantee** modality.
  * **Syntax:** `*a` or `a *{Guarantee}` (defaulting to `a *{Unique}`).
  * **Meaning:** Signifies that the value has an absolute invariant or guarantee on its reference topology. Most commonly: *"This is the sole reference to this object in the entire heap (no aliases exist)."*
* **`Borrow :: Permission -> Type -> Type`**:
  * **What it is:** The **borrowed reference** type.
  * **Syntax:** `& p a` (e.g., `& 1 a`, `& 1/2 a`, `& f a`).
  * **Meaning:** A temporary capability/reference to an object `a` with access permission `p`. It allows accessing or mutating an object without destroying its unique ownership.

#### `Guarantee` vs `Permission`
In Granule's kind system ([`Primitives.hs:L113-L116`](file:///home/srghma/projects/granule/frontend/src/Language/Granule/Checker/Primitives.hs#L113-L116)):
```haskell
-- In Primitives.hs:
(mkId "Uniqueness", (kguarantee, [], []))
(mkId "Unique",     (tyCon "Uniqueness", [], []))
(mkId "Fraction",   (tyCon "Permission", [], []))
```
* **`Guarantee` (Kind of `Star`):**
  * Describes **what is guaranteed** about the reference in isolation.
  * Built-in guarantees:
    * `Unique`: Absolute unaliased ownership.
    * `Trusted`: Used in information-flow control ([`reveal : a *{Trusted} -> a [Lo]`](file:///home/srghma/projects/granule/frontend/src/Language/Granule/Checker/Primitives.hs#L673)).
* **`Permission` (Kind of `Borrow`):**
  * Describes **what access rights** the borrower currently holds using **fractional permissions** (Boyland's fractional permission model):
    * Permission `1` (or `Star` permission): **Full permission** $\implies$ Allows **in-place mutation and reading** (`{mut f}`).
    * Permission `f < 1` (e.g. `1/2`, `1/4`): **Read-only permission** $\implies$ Can be split and shared among concurrent threads!

This file demonstrates splitting a borrow `& 1` into two read-only fractional borrows `& 1/2` to perform parallel computation, then re-joining them:

```haskell
import Parallel
import Prelude
import Vec

--- Convert an indexed natural number to an untyped int
natToInt'
  : forall {n : Nat}
  . N n -> Int
natToInt' Z = 0;
natToInt' (S m) = 1 + natToInt' m

toFloatArray : forall {n : Nat} . Vec n Float -> exists {id : Name} . *(FloatArray id)
toFloatArray v =
  let (n', v) = length' v
  in unpack <id, arr> = newFloatArray (natToInt' n')
  in pack <id, (toFloatArrayAux arr [0] v)> as exists {id : Name} . *(FloatArray id)

toFloatArrayAux : forall {n : Nat, id : Name} . *(FloatArray id) -> Int [n] -> Vec n Float -> *(FloatArray id)
toFloatArrayAux a [n] Nil = a;
toFloatArrayAux a [n] (Cons x xs) =
  toFloatArrayAux (writeFloatArray a n x) [n + 1] xs

sumFromTo : forall {id : Name, f : Fraction} . & f (FloatArray id) ->  !Int -> !Int -> (Float, & f (FloatArray id))
sumFromTo array [i] [n] =
  if i == n
    then (0.0, array)
    else
      let (x, a) = readFloatArray array i;
          (y, arr) = sumFromTo a [i+1] [n]
      in  (x + y, arr)

-- A reference to a droppable value can be written to without violating linearity
writeRef : forall {a : Type, id : Name} . {Dropable a} => a -> & 1 (Ref id a) -> & 1 (Ref id a)
writeRef x r = let
    (y, r') = swapRef r x;
    () = drop@a y in r'

parSum : forall {id id' : Name} . *(FloatArray id) -> *(Ref id' Float) -> *(Ref id' Float, FloatArray id)
parSum array ref = let
     ([n], array) : (!Int, *(FloatArray id))     = lengthFloatArray array;
     compIn                                      = borrowPull (ref, array)
  in flip withBorrow compIn (\compIn ->

                let (ref, array)      = borrowPush compIn;
                    (array1, array2)  = split array;

                    -- Compute in parallel
                    ((x, array1), (y, array2)) =
                                par (\() -> sumFromTo array1 [0] [div n 2])
                                    (\() -> sumFromTo array2 [div n 2] [n]);

                    -- Update the reference
                    ref'        = writeRef ((x : Float) + y) ref;
                    compOut     = borrowPull (ref', join (array1, array2))

                  in compOut)

main : Float
main =
  unpack <id , arr> = toFloatArray (Cons 10.0 (Cons 20.0 (Cons 30.0 (Cons 40.0 Nil)))) in
  unpack <id', ref> = newRef 0.0 in
  let
      (result, array) = borrowPush (parSum arr ref);
      () = deleteFloatArray array
  in freezeRef result
```

### Part 2: `TyRational` vs `TyFraction`

Both wrap Haskell's `Rational` in the AST, but they inhabit completely different type kinds and serve different purposes:

| Feature | `TyRational` | `TyFraction` |
| :--- | :--- | :--- |
| **AST Constructor** | `TyRational :: Rational -> Type` | `TyFraction :: Rational -> Type` |
| **Kind** | `Q` / `Float` (Coeffect Semiring) | `Permission` / `Fraction` |
| **Parser Syntax** | Floats like `0.5`, `1.5` | Fractional ratios `1/2`, `2/4`, `1` |
| **Domain** | **Resource coeffects** (Differential privacy, sensitivity analysis, continuous consumption) | **Borrowing permissions** (Fractional permissions for shared read vs exclusive write) |
| **Example** | `a [0.5]` (e.g. in differential privacy or metric spaces) | `& 1/2 a` (e.g. read-only borrowed alias) |

### Part 3: Complete Breakdown of `data Type`

```haskell
data Type where
```

#### Core & Functional Syntax
* **`Type :: Int -> Type`**
  * Universe levels ($Type_0, Type_1, \dots$). In Granule, kinds are themselves types. `Type 0` is the universe of standard types.
* **`FunTy :: Maybe Id -> Maybe Coeffect -> Type -> Type -> Type`**
  * Function arrow $A \to B$.
  * `Maybe Id`: For dependent function binders `(x : A) -> B`.
  * `Maybe Coeffect`: The grade on the arrow in `GradedBase` mode (`A % r -> B`). If `Nothing`, it is standard linear `A -> B`.
* **`TyCon :: Id -> Type`**
  * Type constructor constant (e.g., `Int`, `Float`, `Vec`, `Unique`, `Nat`, `IO`).
* **`TyVar :: Id -> Type`**
  * Type variable identifier (e.g., `a`, `b`, `n`, `r`).
* **`TyApp :: Type -> Type -> Type`**
  * Type application `T1 T2` (e.g., `Vec n a` is `TyApp (TyApp (TyCon "Vec") (TyVar "n")) (TyVar "a")`).

#### Modalities: Coeffects, Effects, Ownership
* **`Box :: Coeffect -> Type -> Type`**
  * Graded modal necessity $\Box_r A$, written `a [r]`. Represents coeffects (e.g. usage demand, sensitivity, privacy).
* **`Diamond :: Effect -> Type -> Type`**
  * Graded modal possibility $\Diamond_e A$, written `a <e>` (e.g. `Int <IO>`, `a <{Stdout}>`). Represents computational monads/effects.
* **`Star :: Guarantee -> Type -> Type`**
  * Uniqueness guarantee: `*a` or `a *{Unique}`. Guarantees no existing aliases in the heap.
* **`Borrow :: Permission -> Type -> Type`**
  * Borrowed reference: `& p a`. Represents an alias with access permission $p$.

#### Type-Level Numbers & Quantities
* **`TyInt :: Int -> Type`**
  * Type-level natural/integer literal (e.g., vector length `Vec 3 Int`, or discrete grade `a [2]`).
* **`TyRational :: Rational -> Type`**
  * Continuous numeric coeffect (parsed from floats, e.g. `a [0.5]`).
* **`TyFraction :: Rational -> Type`**
  * Fractional borrow permission (parsed from `n/d`, e.g. `& 1/2 a`).
* **`TyGrade :: Maybe Type -> Int -> Type`**
  * A grade literal explicitly or implicitly tagged with its semiring kind (e.g., `1 : Nat`, `0 : ExtNat`).
* **`TyInfix :: TypeOperator -> Type -> Type -> Type`**
  * Infix type-level operators:
    * *Semiring algebra:* `+`, `*`, `-`, `^`, `/\` (meet), `\/` (join), `..` (intervals `[0..1]`).
    * *Type operators:* `×` (pair type), `&` (additive product).
    * *Predicate constraints:* `==`, `<=`, `. <=`, `=>`.

#### Sets & Type Families
* **`TySet :: Polarity -> [Type] -> Type`**
  * Type-level set: `{Stdout, Stderr}`.
  * `Polarity`:
    * `Normal`: Standard set ordered by subset inclusion (e.g., effects produced).
    * `Opposite` (written `{...}.`): Dual ordering where larger sets are lower in the lattice (used for capability requirements and security clearance).
* **`TyCase :: Type -> [(Type, Type)] -> Type`**
  * Type-level pattern matching (type-level `case T of P1 -> T1; P2 -> T2`).

#### Signatures & Quantifiers
* **`TySig :: Type -> Kind -> Type`**
  * Explicit kind annotations at the type level: `T : K` (e.g., `0 : s` or `r : Nat`).
* **`TyExists :: Id -> Kind -> Type -> Type`**
  * Existential quantification: `exists {id : K} . T`.

* **`TyForall :: Id -> Kind -> Type -> Type`**
  * Universal quantification / Rank-N polymorphism: `forall {a : Type} . T`.
* **`TyName :: Int -> Type`**
  * Internal compiler-generated unique type variable index.

### 1. Which types are supported as indices?

In Granule, type indices are values from the **grade / sort / index** universe that can appear in types. Because Granule integrates coeffects and indexed types under the same constraint framework, the supported index sorts are the ones Granule can represent and solve symbolically:

* **`Nat`** (natural numbers, $\mathbb{N} \ge 0$): The primary index sort used for length-indexed vectors (`Vec (n : Nat) a`), finite sets ([`Fin (n : Nat)`](file:///home/srghma/projects/granule/StdLib/Fin.gr#L16)), matrix dimensions, etc.
* **`Q` / `Fraction`**: Rational / fractional quantities (used for fractional permissions and probabilities).
* **`Ext k`**: Extensions with infinity ($\infty$), e.g., `Ext Nat`.
* **`Interval k`**: Lower- and upper-bound intervals over another index sort $k$.
* **`(k1, k2)`**: Products / tuples of index sorts.
* **`Set k`**: Finite sets of constructors over closed types.
* **Discrete / Lattice sorts**:
  * **`Sec` / `Level`**: Security classifications (`Public`, `Private`, `Hi`, `Lo`).
  * **`LNL`**: Linear / non-linear modalities (`Zero`, `One`, `Many`).
  * **`OOZ`**: $\mathbb{Z}_2$ (`0` or `1`).
* **`Type`**: Standard GADT-style type equality indexing (e.g. indexing by `Int`, `Bool`, etc.).

### What is `Hsup` ($\⨱$)?

`Hsup` stands for **Homomorphic supremum / "pushable" condition**. 

It represents the condition under which a graded modal box $[c]$ can be **pushed / distributed** over a multi-ary data constructor or pair:
$$\text{push} : (A \times B)[c] \to A[c] \times B[c]$$

In Granule:
* `{Pushable c}` in the stdlib ([`Prelude.gr:L113`](file:///home/srghma/projects/granule/StdLib/Prelude.gr#L113)) is syntactic sugar for `{c ⨱ c}` (defined in [`Primitives.hs:L29`](file:///home/srghma/projects/granule/frontend/src/Language/Granule/Checker/Primitives.hs#L29)).
* When you pattern match on a boxed data constructor with multiple arguments ($> 1$), Granule emits an `Hsup` constraint ([`Patterns.hs:L201`](file:///home/srghma/projects/granule/frontend/src/Language/Granule/Checker/Patterns.hs#L201)):
  ```haskell
  -- Hsup if you only have more than one premise (and have an enclosing grade)
  Just (coeff, coeffTy) | length ps > 1 ->
    addConstraintToNextFrame (Hsup s coeff coeff coeffTy)
  ```

### How `Hsup` is compiled and submitted to SBV

The compilation to SBV happens in **3 stages**:

#### 1. In the Constraint Compiler ([`Constraints.hs:L301-303`](file:///home/srghma/projects/granule/frontend/src/Language/Granule/Checker/Constraints.hs#L301-L303))
When `compile` visits an `Hsup` constraint:
```haskell
compile vars (Hsup _ c1 c2 t) =
  bindM2And' (\c1' c2' -> pure (symGradeHsup c1' c2'))
             (compileCoeffect (normalise c1) t vars)
             (compileCoeffect (normalise c2) t vars)
```
1. `c1` and `c2` are compiled to symbolic grades (`SGrade`).
2. They are passed to `symGradeHsup c1' c2'`, which returns an SBV boolean expression (`SBool`).

---

#### 2. The `symGradeHsup` Function ([`SymbolicGrades.hs:L434-443`](file:///home/srghma/projects/granule/frontend/src/Language/Granule/Checker/Constraints/SymbolicGrades.hs#L434-L443))
This is where the actual SBV formula is generated depending on the semiring:

```haskell
symGradeHsup :: SGrade -> SGrade -> SBool
-- | For LNL grades, when both grades are linear allow pushing, otherwise, pushing is disallowed.
-- | Check the grades are concrete to disallow hsup on grades which are polymorphic within the LNL semiring.
symGradeHsup (SLNL n) (SLNL m) | isConcrete m, isConcrete n = n .== literal oneRep .&& m .== literal oneRep
symGradeHsup (SLNL n) (SLNL m) = sFalse

-- | Disallow hsup for polymorphic grades
symGradeHsup (SUnknown s1) (SUnknown s2) = sFalse

-- | For extended grades (Ext r), recurse into the base grade
symGradeHsup (SExt r _) (SExt r' _) = symGradeHsup r r'

-- | For all other grades, allow pushing
symGradeHsup s1 s2 = sTrue
```

The logic submitted to SBV is:
* **For `LNL` (Linear / Non-Linear semiring)**:
  * Pushing a non-linear or zero box is unsound because distributing it alters resource bounds.
  * If concrete, it generates an SBV equality assertion:
    $$\mathtt{n == 1 \land m == 1}$$
    (i.e. pushing is **only allowed if both are strictly linear `One`**).
  * If not concrete, it yields SBV `sFalse`.
* **For unknown / polymorphic grades (`SUnknown`)**:
  * Pushing cannot be guaranteed sound in general, so it yields SBV `sFalse` (unless eliminated earlier by [`handleHsupPoly`](file:///home/srghma/projects/granule/frontend/src/Language/Granule/Checker/Checker.hs#L2417)).
* **For standard semirings (`Nat`, `Q`, `Interval`, etc.)**:
  * Pushing is always sound, so it returns SBV `sTrue`.

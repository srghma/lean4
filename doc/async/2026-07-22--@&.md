**borrowing**

> **A borrowed parameter is not consumed by the callee. Ownership stays with the caller (outside).** The callee (that insides of called function) may read it but must not `dec` it (to not destroy by inadvertedly) (and the caller must not `inc` !!! before passing). Whoever *owns* it is responsible for the eventual `dec`.

```lean
-- src/Init/Core.lean:147
@[extern "lean_thunk_get_own"] protected def Thunk.get (x : @& Thunk α) : α := ...
-- src/Init/Data/Array/Basic.lean:166
def usize (xs : @& Array α) : USize := xs.size.toUSize
```


For `@[extern]` functions like `lean_string_append`

```
@& in source  →  markBorrowed / isMarkedBorrowed (BorrowedAnnotation.lean)
              →  Param.borrow : Bool          (LCNF/Basic.lean:68)
              →  InferBorrow / PropagateBorrow (infer more borrows automatically)
              →  ExplicitRC.lean              ← THE pass that skips inc/dec
              →  EmitC.lean_ / EmitRust.lean  ← dumb printers
```

`BorrowedAnnotation.lean` is trivial — just tags an `Expr`:
```lean
def markBorrowed   (e : Expr) : Expr := mkAnnotation `borrowed e
def isMarkedBorrowed (e : Expr) : Bool := annotation? `borrowed e |>.isSome
```
which becomes the `borrow` field on the parameter (`LCNF/Basic.lean:68`, and `IR/Basic.lean:210`). The IR pretty-printer shows it as `@&`:
```lean
-- src/Lean/Compiler/IR/Format.lean:85
| { x := name, borrow := b, ty := ty } => "(" ++ name ++ " : " ++ (if b then "@& " else "") ++ ty ++ ")"
```

## 3. Where borrow actually does its work — `ExplicitRC`, not the emitter

This is the key insight: **borrow is entirely resolved during RC insertion.** By emit time the `inc`/`dec` are already explicit `FnBody` nodes; the emitters just print whatever nodes exist.

`ExplicitRC.lean` marks borrowed params as "borrowed values" and then never inserts a `dec` for them:

```lean
-- src/Lean/Compiler/LCNF/ExplicitRC.lean:100
def visitParam (p : Param .impure) : M Unit := do
  addDerivedValue #[] p.fvarId
  if p.borrow && p.type.isPossibleRef then
    addBorrowedValue p.fvarId          -- ← this value will never be dec'd
```

The header comment spells out the whole point (`ExplicitRC.lean:22-26`): borrowed params *"avoid performing the majority of reference counting"*, plus **derived borrows** — anything projected out of a borrowed value is itself treated as borrowed (safe, because a borrowed value won't be mutated/freed under you). Live-variable tracking even keeps a dedicated `borrows` set that *"can thus never be freed"* !!!!! (`ExplicitRC.lean:185`).

Correspondingly, when an argument lands in a *borrowed* parameter slot, no `inc` is inserted (e.g. `FloatLetIn.lean:152` gates on `sig.params[i]?.any (·.borrow)`).

## 4. The C++ runtime side (`origin-master-src`) — pure documentation

On the runtime side the borrow convention is only a **documenting typedef** — all four are literally `lean_object *`:

```c
/* origin-master-src/include/lean/lean.h:175-180 */
/* The following typedef's are used to document the calling convention for the primitives. */
typedef lean_object * lean_obj_arg;   /* Standard (owned) object argument. */
typedef lean_object * b_lean_obj_arg; /* Borrowed object argument.        */
typedef lean_object * u_lean_obj_arg; /* Unique (non-shared) argument.    */
typedef lean_object * lean_obj_res;   /* Standard object result.          */
typedef lean_object * b_lean_obj_res; /* Borrowed object result.          */
```

This is exactly your `lean_string_append(lean_obj_arg s1, b_lean_obj_arg s2)` example: `s1` is owned → the function `dec_ref(s1)`s it internally; `s2` is borrowed → the function *never* touches its refcount, the caller keeps it. The `@&` on the Lean-side signature of that extern is what tells `ExplicitRC` "don't you dare emit a dec for arg 2 — the C code isn't expecting to own it."

## 5. EmitC vs EmitRust — both are "dumb," and neither changes the *type*

```lean
-- src/Lean/Compiler/LCNF/EmitRust.lean:35
def leanObjectPtrTy : String := s!"*mut {leanObjectTy}"   -- = *mut lean_object
-- toRustType, line 49:
| object => leanObjectPtrTy    -- borrowed or owned → identical Rust type
```
No `&T`, no lifetime — just a raw pointer, matching C's ABI.

The inc/dec themselves are emitted identically to C, straight from the RC nodes:
```lean
-- src/Lean/Compiler/LCNF/EmitRust.lean:996
| .inc fvarId n check persistent k =>
    unless persistent do emitInc fvarId n check   -- → lean_inc / lean_inc_ref
| .dec fvarId n check persistent objs? k =>
    unless persistent do emitDec fvarId n check objs?  -- → lean_dec / lean_dec_ref
```

> Where is it being decided what and where insert inc/dec?


`EmitC`/`EmitRust` **do not decide any of this** — they're dumb printers. Every inc/dec in my examples was already inserted, as explicit `.inc`/`.dec` nodes, by the RC pass. The decision happens in four stages, all upstream of the emitter:

## Stage A — `@&` becomes `param.borrow`

The source `@& String` is an `Expr` annotation (`BorrowedAnnotation.lean`: `markBorrowed`/`isMarkedBorrowed`). When LCNF turns the function type into a parameter list, it reads that annotation:

```lean
-- src/Lean/Compiler/LCNF/Bind.lean:96
let p ← mkAuxParam d (isMarkedBorrowed d)   -- `t : @& String`  ⇒  param.borrow = true
```

So `t : @& String` ⇒ `param.borrow = true`; plain `t : String` ⇒ `param.borrow = false`. **This is the single bit that separates your question 1 from question 2.**

## Stage B — `InferBorrow` refines it, but leaves `@[extern]` alone

For an ordinary `def`, `InferBorrow.lean` runs dataflow and may flip params to borrowed for performance — *unless you wrote an explicit `@&`*, which it preserves:

```lean
-- InferBorrow.lean:45-48 (doc)  "heuristics will be ignored if there is a user-defined borrow annotation"
-- InferBorrow.lean:98-99        annotatedBorrows keeps params where `p.borrow` is already set
```

For `String.append`, which is `@[extern]`, inference does *nothing at all*:

```lean
-- src/Lean/Compiler/LCNF/InferBorrow.lean:102
| .extern .. => return ()
```

That's *why* the `@&` on an extern is authoritative and must match the hand-written C — nothing downstream will second-guess it.

## Stage C — `ExplicitRC` reads `param.borrow` and decides the inc/dec

This is where your two code snippets are actually produced. `ps` = the callee's params (here `String.append`'s, with `ps[1].borrow` = the `t`/`@&` bit).

**Caller-side `inc` (the `lean_inc(t)` in the `keep` mistake):**
```lean
-- ExplicitRC.lean:506-508
def addIncBefore (args) (ps) (k) :=
  addIncBeforeAux args (fun i => !ps[i]!.borrow) k   -- predicate = "is this position CONSUMED?"
```
`!ps[i].borrow` is the "consumed" test. Borrowed (`@&`) ⇒ predicate false ⇒ position doesn't consume ⇒ **no inc** (question 1). Owned ⇒ predicate true ⇒ consumed ⇒ `inc` is inserted when the value is still live afterward (question 2).

**Caller-side `dec` (the `lean_dec(t)` in `once` with `@&`):**
```lean
-- ExplicitRC.lean:521-540
def addDecAfterFullApp (args) (ps) (k) := ...
  if info.isPossibleRef && isFirstOcc args i
      && isBorrowParam fvarId args ps   -- ps[i].borrow was true
      && !(← isLive fvarId)             -- not used again
      && !(← isBorrowed fvarId) then
    k ← addDec fvarId k                 -- ← this is the lean_dec(t)
```
Borrowed + last use ⇒ the caller still owns it and the callee didn't take it ⇒ insert `dec`. Owned ⇒ `isBorrowParam` is false ⇒ **no dec** ⇒ (with the borrowing C impl) the leak.

**Callee-side (why a borrowed param is never `dec`'d in its own body):**
```lean
-- ExplicitRC.lean:100-103
def visitParam (p) := do
  if p.borrow && p.type.isPossibleRef then addBorrowedValue p.fvarId   -- goes into `borrows`
-- ExplicitRC.lean:256   isBorrowed → checks the `borrows` liveset; borrowed values are never freed
```
(For `String.append` this rule is enforced by hand in the C — the `@&` is the promise that the C keeps.)

## Stage D — the emitter just prints the nodes

```lean
-- src/Lean/Compiler/LCNF/EmitRust.lean:996-1001
| .inc fvarId n check persistent k => unless persistent do emitInc fvarId n check   -- → lean_inc / lean_inc_ref
| .dec fvarId n check persistent objs? k => unless persistent do emitDec fvarId n check objs?  -- → lean_dec / lean_dec_ref
```
`EmitC.lean_` is identical in spirit. Neither ever looks at `param.borrow` — by the time they run, the `lean_inc(t)`/`lean_dec(t)` from my examples either exist as nodes or don't.

## Map back to the two answers

|                            | question 1 (`@&`)           | question 2 (owned)          |
| -------------------------- | --------------------------- | --------------------------- |
| Stage A sets               | `ps[1].borrow = true`       | `ps[1].borrow = false`      |
| `addIncBefore` (`!borrow`) | no `inc`                    | `inc` when `t` still live   |
| `addDecAfterFullApp`       | inserts `lean_dec(t)`       | inserts nothing             |
| emitter                    | prints those nodes verbatim | prints those nodes verbatim |

So the "where" is: **`Bind.lean:96` reads the `@&`, `InferBorrow.lean:102` leaves the extern's copy intact, and `ExplicitRC.lean:508` & `:537` turn that one boolean into the presence/absence of `lean_inc`/`lean_dec`.** The emitters are the last, decision-free step.
